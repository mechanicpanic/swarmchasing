# 2026-10-02 — the wiki as messages, not pages (`prepare/wiki_msgs.py`, corpus `wiki_msgs`)

## What the export holds that we did not use
- `revisions.hunks`: which lines each save changed. Indices are into `body.split("\n")` (equal to `lines` on all 14,591
  revisions); applying the hunks to the base revision rebuilds every body exactly (14,591 / 14,591). So one row per
  hunk = the text a save added or took away, with label, /16, page and time. 17 revisions have unpublished earlier
  versions: their "add" is the whole page.
- Event fields we had dropped: `request_action`, `param_family` (probes), `round_id`, `success_observed`, `time_grade`.
- `links.jsonl` (23,877 URLs, `followed`), the rmn.re shortener log (499 links) — read only, never follow short links.
- Not released (manifest `source_scan`): ~2.7 M dse request-log rows, ~910 k attacklog rows, 40,596 save requests up
  to 2026-08-27 (we hold 14,591 revisions ending 2026-07-14). A request-level stream exists only on the publishers' side.

## The stream
26,655 rows: add 15,402 · remove 5,931 · delete 5,217 · probe 101 · revert 4.
`text_key` = hash of the normalised text; none for the redaction marker (`[pre-2026 line withheld]`, 139 rows) and the
wiki's own new-page template ("Describe the new page here." / "Beschreibe hier die neue Seite."), which compare equal
without being one message. `add_type`: new 12,127 · readd 1,529 (already on this page) · copy 1,062 (seen only on other
pages) · no key 684. `author_label` on removes = who first added that text on the page; `by_other` = the remover is
someone else.
Limit: authorship is per line as last shaped — an edited line (a signature appended, one letter changed) is a NEW text
under the editor, not a copy; a copy here is an exact re-insertion.

## Findings (server `wiki_msgs`, null = add times shuffled within the UTC day, `runs/null_twin.py --data
data/wiki_msgs.parquet --type-field kind --shuffle add --key day`, n=100)
| # | Question | Real | Null median / 95th / max | Board label |
|---|---|---|---|---|
| R1 | same text, another label, **another page**, within 10 min | 641 | 375 / 387 / 391 | `relay-other-page-10min` |
| R2 | another label removes an author's text, the author puts it back **on the same page** within 1 min | 705 | 305.5 / 360 / 401 | `restore-war-1min` |
```
R1  SELECT field(kind, add) AND field(text_key, $t) AND field(label, $a) AND field(page, $p) FOLLOWED_BY field(kind, add) AND field(text_key, $t) AND field(label, !$a) AND field(page, !$p) DURING 10 minutes
R2  SELECT field(kind, remove) AND field(by_other, true) AND field(author_label, $a) AND field(text_key, $t) AND field(page, $p) FOLLOWED_BY field(kind, add) AND field(text_key, $t) AND field(label, $a) AND field(page, $p) DURING 1 minute
```
The null tests timing within a day only; it breaks "within minutes", not "on the same day" (the June 18 burst stays
in the null). Page is in the query, not `add_type`: `add_type` is computed from the real order and would leak into the null.

R2 is one place and one evening: 691 of 705 restores are on `dse~WillkommenImWiki` (the hub page), June 18 19:00–22:00
UTC, median gap remove → restore 2 s. Pairs: LinkHelper771 → AgentMassPointer13 81, AgentRelent → AgentMassPointer13 73,
AgentRelent → AgentMassFinal13 45. Labels stay, networks rotate: on that page AgentRelent saves 381 times from 96
different /16s in 75 min, AgentMassPointer13 183 times from 81 /16s in 15 min. Reading (not proven): a tug of war over
the shared board between a few persistent names, each edit leaving from a fresh cloud address.
R1 top texts: the "Loop predicted child raw investor" broadcast — 314 pages, 58 labels, 89 /16s, 5 minutes (June 18
20:09); `#REDIRECT ApiReferencesForResearch` on 15 pages by 13 labels.

Language note → prismql: `field(label, !$a)` in the SAME leg that binds `$a` errors in a one-leg query ("refers to a
variable no earlier leg binds") but is accepted when the query has a second leg — inconsistent; worked around with a
`by_other` column.
